---
name: init
description: "Create or refresh this project's crew profile (.claude/crew/profile.md) by scanning the repo and asking for what cannot be inferred; ensures the designs directory, tracker labels and a CLAUDE.md pointer. Run once per project."
argument-hint: "[--refresh]"
disable-model-invocation: true
---

You are setting up the crew for this project. Work in `${CLAUDE_PROJECT_DIR}`.

1. **Scan, do not ask, for what the repo shows.** Languages and frameworks (project files, package manifests, lock files), app and service folders, test runners and their commands, scripts directory, CLAUDE.md, docs folders, git remote (tracker candidate), default branch, IaC and deploy scripts, identity provider, cloud SDKs, event store or messaging libraries. Fill `generated:` from the same scan — generator output directories, `*.g.*`, `Generated/`, lock files, vendored or generated client folders — and write the line as `generated: <globs>  # guessed by /crew:init — verify`, so the warning stands in the file the next reader opens rather than only in this run's report. `crew_profile_value` strips a trailing `# …`, so the value stays exactly the globs. Report it as **guessed** as well. Its absence is the safe direction: with no globs declared every changed file counts toward the size cap, so a project with a large generated surface feels the cap as too tight and declares its globs in one edit, which beats silently excluding a set nobody checked.
2. **Read the template** `${CLAUDE_PLUGIN_ROOT}/templates/profile.md` and draft every line you can fill from the scan. Mark each role `disabled` when the repo shows no trace of that discipline; keep it enabled when in doubt and say so.
3. **Ask the user, in one AskUserQuestion call, only for:** mode (`optional` or `always`), roles to force on or off, exclusive lanes (shared clusters, databases, deploy targets), definition-of-done items beyond "gates green", the tracker if the remote is ambiguous, and the three item-shape keys the repo cannot show — `size-cap:` (the most hand-written files one task may touch; offer 15 as the default and `-` as "no cap, `Size:` still counted"), `definition-of-done:` (a path or a section name; absent, it is the profile's own Definition of done section) and `merge-authority:` (who may merge; absent, the author). Leaving a key out is a supported answer: every absent key falls back to a stated default that the rendered item body shows, so the crew runs unchanged on a profile that declares none of them.
4. **Write** `.claude/crew/profile.md`. Keep it under 80 lines: link to CLAUDE.md sections instead of copying them; put repeated incidents in "Gotchas" as one line each with a pointer. Then **create the directory the profile's `designs:` line names, if it is not already there** — `/crew:plan` writes a design into it as its first act, and a path that is not there surfaces as a failed write inside a plan rather than here, where it costs one `mkdir`. Create it empty; do not put a placeholder file in it. Report it as created, as already present, or — if the value is a path you will not create unasked, an absolute path or one outside the project, or `designs:` has no value at all — say in the report that the directory does not exist, which value you read, and that `/crew:plan` will fail on it until the user fixes the line. Never silently skip it.
5. **On `--refresh` only: offer what the installed template has and this profile lacks — one at a time, as a diff, written only on a yes.** Follow `/crew:conform`'s steps 2 and 4 rather than inventing a second idiom: draft only what is countable, show the diff, wait, and write nothing else. Two sets are compared and nothing else is:

   - **Profile keys, by key name.** The template's top-matter keys — `mode:`, `tracker:`, `default-branch:`, `branch-pattern:`, `designs:`, `generated:`, `size-cap:`, `definition-of-done:`, `merge-authority:` — against the keys the profile declares. `crew_profile_value` reads a key as `^<key>:` and nothing else, so the set of names on each side is the whole comparison. A key **lacks** when the profile has no `^<key>:` line at all, or carries one whose value is still the template's `<…>` placeholder — which every consumer reads as that literal string rather than as the absent-key fallback, so it is worse than absent. Values are never compared, and a key the profile has but the template does not is the project's own and is never mentioned. That is why a profile a project has rewritten in its own words produces no noise: rewording a value, a comment, a role line, a whole section, or reordering the file cannot change which key names are present.
   - **Definition-of-done items, by the rule each one states.** Resolve the project's list the way a task body does — the path or section name `definition-of-done:` gives, else the profile's own "Definition of done" section — and read it whole. For each bullet of the template's section other than its `<project-specific item>` placeholder, ask whether that list already states the same rule **in any words**: a bullet that says it differently, more strictly, or as a deliberate exclusion ("this project ships nothing, so no release is ever owed") states it, and is not offered. Only a rule no bullet speaks to is offered. The comparison is on the rule and never on the text, because a project is expected to reword and a textual diff would offer every bullet on every refresh. When the resolved list is a file other than the profile, the diff is against that file and the rule goes only there — never into the profile as well, which would put one rule in two places. When `definition-of-done:` names a path you cannot read, offer nothing from this half and say which value you read.

   Offer each one alone: what it is, the installed version it comes from (`version` in `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`), a unified diff of the one file it would change, and then stop and wait. There is no batch yes. A no leaves the file exactly as it stands and is recorded in the report. **No answer is not an answer** — in a non-interactive run, a piped or empty stdin, a dispatch into a subagent, any context where waiting returns nothing: print the diffs you would have shown, say that nothing was written, and offer none of them. This step only ever inserts: it never rewrites an existing line, never reorders a section and never removes anything, so a hand edit cannot be overwritten by it.

   **It cannot tell a deliberate deletion from a never-offered item, and does not pretend to.** Nothing records what a past refresh offered or what was declined, so a declined definition-of-done item is offered again at the next refresh, and so is a declined key. Say that in the offer. The way to make a deletion stick is to write the refusal into the project's own list as one line of deliberate exclusion — which the rule-level comparison above then honours, because the rule is spoken to — and the way to stop a key being offered is to declare it with the value the project wants, including the literal `-` where the template documents one.

6. **Role addenda** only where the repo has rules a persona could not infer (for example a generated-copy rule for shared UI, a handler-registration rule for a worker): `.claude/crew/roles/<role>.md` from `${CLAUDE_PLUGIN_ROOT}/templates/role-addendum.md`, at most a few lines each.
7. **Tracker:** run `${CLAUDE_PLUGIN_ROOT}/scripts/tracker.sh ensure-labels` when the tracker is GitHub. Quote its output. Then, for a `github` tracker only, **offer — off by default, never done unless the user says yes** — to render `.github/ISSUE_TEMPLATE/{story,task,bug,tech-debt}.md` from `${CLAUDE_PLUGIN_ROOT}/templates/item-<kind>.md`, so a human filing through the GitHub web UI meets the same shape. They are a convenience render for humans and never a source the crew reads. Give each one the header

   ```
   <!-- Generated by /crew:init from crew <version>. Do not hand-edit: re-run /crew:init --refresh after a plugin upgrade, or take ownership by moving it to .claude/crew/items/<kind>.md. -->
   ```

   with `<version>` read from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`, which is what lets `/crew:status` say when the render lags the installed plugin.
8. **CLAUDE.md pointer:** if CLAUDE.md lacks a "Crew" section, append five lines: crew profile location, how to enter crew mode, the pipeline commands, where personas live, and that the profile wins over persona defaults. **If there is no CLAUDE.md at all, write one** holding a one-line statement of what the project is and that same "Crew" section, and say in the report that you created it rather than appended to it, so the user can rewrite or delete a file they did not have. That file is where every future session learns the crew exists, so the absent-file case is the one that most needs it, and creating a short file is less invasive than the append this step already does unasked to a file full of the user's own writing. Report either way — created, appended, or already carrying a "Crew" section and left alone.
9. Report what was inferred, what was asked, what you created and what you guessed — `generated:` among the guesses, with the globs you chose. Name in the report that each item shape is the plugin's until the project takes one over by placing its own copy at `.claude/crew/items/<kind>.md` (`story`, `task`, `bug`, `tech-debt`), that such a copy decides that kind's sections and their order but not a task's `Story: <sigil><n>` first line or its `Blocked by:`, `Role:` and `Size:` lines — the adapter enforces those four whatever the copy contains, because the board's rollup reads them and an item without them is invisible to it — and that the kind then stops receiving improvements from plugin upgrades. Say whether the `.github/ISSUE_TEMPLATE/` render was declined or written. If the board already holds items filed before this shape existed, say so in one line and point at `/crew:conform`; do not touch them here. `--refresh` keeps the user's hand edits and only updates scanned lines — including re-rendering an existing `.github/ISSUE_TEMPLATE/` set to the installed version — and its only other writes are the step 5 offers that were approved: report them as offered-and-accepted, offered-and-declined, or none offered, and say that a declined one is offered again at the next refresh.
