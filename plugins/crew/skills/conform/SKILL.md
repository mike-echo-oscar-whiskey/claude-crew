---
name: conform
description: "Realign a whole story — the story and every task it lists — once: drafts the fixes a body already decides, has the owning role write the rest, has a scout check every claim a body makes about the repository, shows a diff per item with each contradiction as a question, edits an issue body only after you approve it, and leaves one marker that /crew:work reads. A bug, a tech-debt item or --all gets the shape pass alone."
argument-hint: "[<n> | --all]"
disable-model-invocation: true
---

You are the delivery lead for a one-off pass. Target: `$ARGUMENTS` — one item number, or `--all` for the whole board; no argument behaves as `--all`. Read the profile at `${CLAUDE_PROJECT_DIR}/.claude/crew/profile.md` for the tracker, the roles, `generated:` and `size-cap:`. `T=${CLAUDE_PLUGIN_ROOT}/scripts/tracker.sh`.

**The scope is a story, not an item.** A number that is a task: resolve its story — the task's first line `Story: <sigil><n>`, else the one story whose `## Tasks` checklist lists it (`gh issue list --label story --state all --json number,body`); none found is a question, never a guess, and so are two — then conform that story plus every task its `## Tasks` lists. A number that is a story: the same, that story plus every task its `## Tasks` lists. Every item in that scope goes through every step, a lint-clean one included: a body can pass every shape check and still assert something about the repository that is false, which only step 4 sees. A bug or tech-debt number, and `--all`, are the shape pass alone — steps 1, 2, 3, 5 and 6 over the items `lint` fails, no premise check and no marker — exactly as before.

Two rules hold over every step. **No item is ever refused, reshaped or unclaimed for being old** — a claim warns about a non-conforming body and continues, so this pass is a convenience and never a gate anyone must pass first. **Nothing on the board is edited before step 5 has shown you the diff and you have said yes** — no silent rewrite, no background sweep, not even for a one-character header. And when there is nobody to say yes, the pass refuses rather than proceeds — step 5 says so in full.

1. **List what fails.** Run `bash $T lint --all` (`lint <n>` per item for a story scope, or for a single bug or tech-debt item) and quote it whole: one line per failing item as `#<n>`, its kind, then its failing checks, closing with `N conforming, M not`. Exit 1 only means M is not 0; it is the report working. Exit 2 **with a closing line** means a kind filled `lint`'s fetch limit, so the list you have is a lower bound: say that before migrating anything, quote the closing line that names the kind and the limit, and read further into that kind with `bash $T lint --kind <kind>`, which gives each kind its own budget. Exit 2 **with no closing line at all** is a different thing — the adapter refusing the profile, an unusable `tracker:` line or a backend it does not implement — which fails before any fetch and prints nothing but stderr: fix the profile and start the pass again rather than narrating a lower-bound board. Stop and say so only when M is 0 **and** the exit was 0. Exit 2 with M of 0 is not a clean board and is never reported as one: it means nothing failed among the items that were read, so say the read was partial, and carry on with whatever did fail. The checks come from each kind's resolved shape, so resolve it the way `/crew:plan` does and name which one you got: `${CLAUDE_PROJECT_DIR}/.claude/crew/items/<kind>.md` — the project's override, which is read instead of the shipped one, not merged with it — else `${CLAUDE_PLUGIN_ROOT}/templates/item-<kind>.md`.

2. **Draft the countable fixes yourself, with no role.** Fetch each failing body — in a story scope every body, since step 4 reads them all — with `gh issue view <n> --json body -q .body > <file>` — not `bash $T show <n>`, which prints a human view of the item and its comments rather than the raw body bytes step 5 has to diff and hand back to `gh issue edit --body-file` — and keep that file: step 5 diffs against it. Write only what is **countable**: a value already recorded somewhere else — the body, the item's own tracker fields, its labels, the profile — and copied from there, so two leads drafting it would produce the same line. Anything that needs a judgement is written, not counted, and belongs to step 3. The countable set is exactly this, and every check `lint` can refuse is in it or in step 3:
   - the `Blocked by:` header line, for a task that lacks it — the item's own `blocked-by:` relations, which `gh issue view <n>` prints, rendered as `<sigil><n>` and comma-separated in the order the tracker lists them, and the literal `none` when it has none.
   - the `Role:` header line, for an item that lacks it — the role named by the item's `role:<name>` label, the label the crew sets when it files the item. With no such label there is nothing to count, so it is a question for step 5 and never a guess; the `· design:` half of that line is written text and belongs to step 3.
   - `Size:` whole, in its one form `<H> hand-written files (+ <G> generated) · <T> RED tests · one PR` — `lint` matches the line entire, so a half-written `Size:` fails exactly as a missing one does and is redrafted entire rather than patched. H is the `## Files` entries matching none of the profile's `generated:` globs and G the ones matching one; with `generated:` absent or `-`, every entry counts toward H. T is the numbered tests in `## Tests`, and `0` only where that section itself declares the task test-free.
   - the literal first line `Story: <sigil><n>` for a task that lacks it, taken from the story whose `## Tasks` checklist lists that task. When no story lists it, that is a question for step 5, never a guess.
   - the `## Proof map` skeleton for a story: one row per criterion id in the body, with Task and Proven by left empty.
   - the `## Proves` line for a task whose body already cites criteria in prose — copy the ids it names and invent none.
   - a **flag, not an edit**, when the counted H is above the profile's `size-cap:` (absent: 15, `-`: no cap): the item needs a `Split line:` and a split before it starts. Never split an item yourself; it is work the old shape was hiding and the split is its own decision.

   Everything else — a TL;DR, a why-it-matters, a done-when, a criterion's text, a split's seam — is new prose a machine cannot write. Do not write it here.

3. **Brief the owning role for the text, one item per brief.** For each item still failing a check after step 2 — a missing **section or a missing header line** alike, since step 2 is the whole countable set and whatever it did not draft is therefore written text — dispatch the role that owns the kind — `crew:product-owner` for a story, `crew:architect` for a task, bug or tech-debt — on the cheapest tier that can do the job, in parallel across items. Each brief carries that one item's body, its failing check lines and the resolved template, and **nothing else**: no second item, no board summary, no history of the pass. Ask for the missing sections as text to paste and for nothing the body does not support — a role that cannot tell says so, and the item arrives at step 5 as a question rather than as an invented sentence. Say in every brief that it is **read-only**: the role returns text and writes nothing, no `gh` or `tracker.sh` call of any kind, no edit, comment, label, assignee or claim on any item. The board is step 5's alone.

4. **Check every premise against the repository (story scope only).** Dispatch one `crew:scout` run per item in the scope, on the tier the README's "Model per role" gives the scout, in parallel across items, at the repository's current `HEAD`. Each brief carries that one item's body as it would stand after steps 2 and 3, and nothing else, and asks for every concrete claim the body makes about what the repository **is** now — a path, a line reference, a symbol, a signature, a config key or seed fact, an exclusivity such as "X only lists Y" — each returned as **verified** (path:line and the quoted line that shows it), **contradicted** (path:line and the quoted line that refutes it), **drift** (the claim holds but the text it cites has moved: the cited reference, then the actual path:line and quoted line) or **unverifiable** (nothing in the tree can answer it). What the item says it *will* change is a plan, not a premise, and is not checked. The brief says the run is **read-only** in the same words as step 3: no edit, no `gh` or `tracker.sh` call. Line-number drift alone is drift, not a contradiction: the corrected reference may enter the proposed body as a countable fix, marked as this step's and shown in the diff like step 2's. A contradiction is never rewritten into the body — not by you, not by a role: it goes to step 5 as a question for the user with both quotes beside it, and so does an unverifiable claim the item's work rests on.

5. **Show a diff per item and wait.** Per item, present the failing checks, the current body against the proposed one as a unified diff, which parts came from step 2, from a role and from step 4, every contradicted or unverifiable premise as a question with the scout's quotes, and every question left open. Build the proposed body by inserting each drafted section at the position the resolved template gives it — in the plugin's story template `## Proof map` sits after `## Out of scope` and before `## Open questions` — and keep `## Tasks` the last section of a story body: `lint` refuses any other last section, and the tracker appends the task checklist to the end of it. Then **stop and wait for the user**, item by item: there is no batch yes. Apply only what is approved — `gh issue edit <n> --body-file <f>` for the body, then `bash $T comment <n> --body-file <f>` for a short note saying which sections this pass changed and that it was proposed and approved, not swept in. Leave a declined item exactly as it stands and record the decline; never touch its labels, its assignee or its claim.

   **No answer is not an answer.** When this step cannot put the question to a human — a non-interactive run such as `claude -p`, a piped or empty stdin, a dispatch into a subagent, any context where waiting would return nothing — it refuses the whole pass instead of proceeding: print the diffs it would have shown, say that no approval could be obtained in this run and that nothing was written, and exit before the first `gh issue edit`, the first `bash $T comment` and the first item. A `--all` run stops at the start, not halfway. Silence, a timeout, an empty line and a default are all a no.

   **Leave one marker on the story (story scope only).** When every item in the scope has had its answer — approved, declined or left open — show the marker comment and, on a yes, post it with `bash $T comment <story> --body-file <f>` after the last body edit of the pass. Its first line is fixed, because `bash $T conformed <n>` finds it by that line and `/crew:work` reads that answer: `crew:conform 2026-10-02T09:00:00Z 57224763` — the literal `crew:conform`, the UTC time as ISO 8601, and `git rev-parse --short HEAD` of the tree step 4 read. Below it: the items that now conform, each declined item and what was declined, and each contradiction the user left open. The story then reads as conformed until its body or one of its tasks' bodies is edited after that comment; a declined marker leaves the story unmarked, and nothing else changes.

6. **Report** in five lists: what now conforms, what needs a split (each with its counted H and the cap), what a role could not answer, each premise left contradicted or unverifiable, and what the user declined — and say whether the marker was posted. Close by re-running `bash $T lint --all` and quoting its closing line as the after-count — exit 2 there makes the after-count a lower bound exactly as it did in step 1, so say so instead of presenting it as the board — and note that a declined or split-pending item will keep appearing in `/crew:status`'s `items:` line until it is dealt with — which is the point, not a failure.
