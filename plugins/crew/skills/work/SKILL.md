name: work
description: "Claim a task issue, work it in an isolated branch with the owning specialist implementing test-first, commit that work, have QA and (when relevant) security review the commit, run the project's gates and open a PR that closes the task. Requires a task issue number."
argument-hint: "#<task-number>"
disable-model-invocation: true
---

You are the delivery lead for this pipeline step. Task: `$ARGUMENTS`. Read the operating model at `${CLAUDE_PLUGIN_ROOT}/templates/operating-model.md` and the profile at `${CLAUDE_PROJECT_DIR}/.claude/crew/profile.md`. `T=${CLAUDE_PLUGIN_ROOT}/scripts/tracker.sh`.

1. **Fetch and claim.** `$T show <n>`; confirm the role label and that `Blocked by` issues are closed. `$T claim <n>` — if it refuses (already claimed), stop and tell the user who holds it.
2. **Isolate.** If not already on a task branch, use EnterWorktree (or `git worktree`) with the profile's branch pattern, from the default branch, freshly pulled. Never work on the default branch.
3. **Implement.** Brief the owning role (`crew:<role>` from the label) with: the task body, the story, the design location, the profile's commands and gotchas, the requirement to work test-first WITH the red run quoted in Verification before the green run, and the output contract. A result without a quoted red run goes back to the role once with that single instruction. Run it. If it returns hand-offs, brief those roles; sequence them.
4. **Commit, then review.** Only after the owning role has returned. Check the working directory (`pwd`), then commit the role's work on the task branch per the user's git rules (check `git config user.name` and `user.email` first) with the message's claims checked against the diff: a reviewed commit is a known state, and review fixes become further commits. When the diff changes code a test protects, the qa-engineer reviews by mutation — it edits and reverts production code — so it gets a worktree of its own, detached at that commit and at a path this run has not used: `git worktree add --detach <path> <task-branch>` (adding the branch itself fails; it is checked out here). Name the path and the commit in its brief. For a docs-only diff, or a script nothing builds or imports, create no worktree: brief QA to review by reading, say in the brief that the mutation review is not applicable to this diff, and the PR says "not applicable". The reading roles stay in the task tree, not QA's. Then in parallel: `crew:qa-engineer` reviews the tests and the red-run evidence, runs the suite under mutation in its worktree, preceded by the same command un-mutated in that same worktree as the baseline, both exit codes quoted — this commit has not been gated yet (that is step 5), and the role's green was a narrower command in another tree, so there is nothing to cite here; `crew:security-engineer` when the task or story touches auth, tenants, secrets, outbound calls or untrusted input; the profile's specialist when the change crosses their domain. Feed findings back to the owning role once; a second round goes to the user. A qa-engineer result recording the mutation as not run means the mutation review has not happened: confirm the worktree is there at the named path and commit (`git -C <path> rev-parse HEAD`), create it only if that fails, and re-brief once with the path and the commit spelled out, before step 5; if QA still records the mutation as not run, the PR body and the report say the mutation review did not run. Remove QA's worktree with `git worktree remove --force <path>` once the review is done — the gate rewrites tracked files while it runs (a regenerated client, an exported contract, a formatter rewrite) and a plain `remove` aborts on them; forcing is safe because QA has proved its mutation reverted and the tree holds nothing that is not in the commit.
5. **Gates and done.** Run the profile's `gates:` command yourself, bare, and quote the exit code, scoped to the diff: code, tests or anything that is built gets the full suite; a docs-only diff, or a script nothing builds or imports, skips it and the PR says so. Walk the profile's definition of done item by item and state each. Missing items: brief `crew:technical-writer` or the owning role; do not skip them.
6. **Commit fixes and PR.** Check the working directory first (`pwd`; the shell's cwd persists and several worktrees may be open), commit the review fixes on the task branch and check the message's claims against the full diff. Push the branch. Open a PR with `gh pr create` whose body follows the user's PR format and contains `Closes #<n>`; mention the story number. `$T release <n> --to in-review`.
7. If blocked at any step: `$T release <n> --to blocked` with a comment explaining why, and report.
8. Report: PR link, roles and their one-line contributions, gate output, remaining open questions. Merging is the user's.
