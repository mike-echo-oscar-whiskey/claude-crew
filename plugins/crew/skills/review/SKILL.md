---
name: review
description: "Review a pull request with the crew in parallel (architect, QA, security, the owning specialist), deduplicate findings and post one review. Accepts a PR number or branch."
argument-hint: "<pr-number|branch>"
disable-model-invocation: true
---

You are the delivery lead for this pipeline step. Target: `$ARGUMENTS`. Read the operating model at `${CLAUDE_PLUGIN_ROOT}/templates/operating-model.md` and the profile at `${CLAUDE_PROJECT_DIR}/.claude/crew/profile.md`.

1. **Collect context.** `gh pr view <target> --json number,title,body,files,baseRefName,headRefName,headRefOid` and `gh pr diff <target>`. Identify the task and story from `Closes #n` and the role label. Then give the review its trees at the PR head, all at `headRefOid` — the commit the diff belongs to — at paths unique to this run, not to the commit, so a re-review of the same head does not land on a previous run's path. The head may live in a fork, so fetch the PR ref rather than the branch name: `git fetch origin pull/<number>/head`, then `git worktree add --detach <readers-path> <headRefOid>` for the reading roles and, when the diff changes code a test protects, `git worktree add --detach <qa-path> <headRefOid>` for the qa-engineer's mutations (for a docs-only diff, or a script nothing builds or imports, QA reviews by reading and its brief says the mutation review is not applicable). Never pass `FETCH_HEAD`: it is one slot any other session's fetch rewrites, and the trees must be the same commit. `worktree add` fails in two ways and they are not the same failure: `fatal: '<path>' already exists` is a tree an earlier run left behind or one this run already created — remove it with `git worktree remove --force <path>` when this pipeline made it, otherwise add at another path, and continue; the review round stands. Only `fatal: invalid reference: <headRefOid>` means the head moved between `gh pr view` and the fetch — re-read the PR and start over. Never switch the lead's checkout — other sessions share it. Remove the worktrees with `git worktree remove --force <path>` once the review is posted; a plain `remove` aborts on whatever the gate rewrote, and the path then stays registered.
2. **Review in parallel**, each briefed with the diff, the task and story, the profile, its worktree path and the reviewed commit (`headRefOid`), and the findings format (file:line, severity P1/P2/P3, what, why, fix):
   - `crew:architect`: structure, layering, contracts, reuse, naming.
   - `crew:qa-engineer`: test quality and coverage of the acceptance criteria; reviews by mutation in its own worktree and runs the suite there under mutation, preceded by the same command un-mutated in that same worktree as the baseline, both exit codes quoted; it may cite a run the PR quotes instead only when that run is the same command on `headRefOid` itself. A result recording the mutation as not run: confirm `<qa-path>` is there at `headRefOid` (`git -C <qa-path> rev-parse HEAD`), create it only if that fails — an `already exists` error here is not the moved head of step 1 — and re-brief once with the path and the commit spelled out; if QA still records the mutation as not run, the posted review says the mutation review did not run.
   - `crew:security-engineer`: when the diff touches auth, tenants, secrets, outbound calls, untrusted input; otherwise skip.
   - The owning specialist (`crew:<role>`): domain correctness.
   - `crew:technical-writer`: only when the profile's definition of done has documentation items.
3. **Deduplicate and rank.** Merge overlapping findings, keep the most severe rating, drop anything without a concrete failure path. P1 blocks.
4. **Post one review** with `gh pr review <target> --comment --body-file <file>` (or `--request-changes` when a P1 exists). Findings grouped by severity, each with file and line.
5. Report: verdict, counts per severity, the P1s in full, which roles reviewed.
