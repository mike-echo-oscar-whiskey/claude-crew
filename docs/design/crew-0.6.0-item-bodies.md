There is **no item template in the plugin at all**. The task shape is prose inside

## 1. Where each template lives and how a project gets it

**Decision: shipped in the plugin, read at runtime, never copied into the project.**

Four files, `plugins/crew/templates/item-story.md`, `item-task.md`, `item-bug.md`,
`item-tech-debt.md`. `refine` reads `${CLAUDE_PLUGIN_ROOT}/templates/item-story.md`; `plan` reads
`item-task.md`; `work` and any role filing a finding read `item-bug.md` / `item-tech-debt.md`. This
is the mechanism `templates/operating-model.md` and `templates/profile.md` already use through
`${CLAUDE_PLUGIN_ROOT}`, so nothing new has to be invented and `plugin install` is the whole
distribution story.

**The override, and how a project declares it.** A skill resolves each kind in this order:

1. `${CLAUDE_PROJECT_DIR}/.claude/crew/items/<kind>.md` — if that file exists, it wins whole;
2. otherwise `${CLAUDE_PLUGIN_ROOT}/templates/item-<kind>.md`.

The file existing **is** the declaration — no profile key, nothing to keep in sync, and it matches
the precedence the plugin already documents (the profile wins over persona defaults). One line at
the top of every shipped template says so, so a reader of the plugin's template knows where the
escape hatch is.

**The trade-off, stated plainly.** A template *written into* a project at init is editable and drifts:
the project keeps a 0.5.9 body shape forever and an improvement in 0.6.0 never reaches it, silently.
A template *read at runtime* upgrades everywhere the moment the plugin upgrades, but cannot be tuned
per project — which is exactly what the override file buys back, at the honest price that **an
overriding project stops receiving improvements to that one kind**, and only that kind. That price
is visible (the file is in the project's git history) rather than invisible (a copy that diverged).
Runtime read is therefore the default and copying is the exception.

**`.github/ISSUE_TEMPLATE/` is a separate, opt-in artifact.** A human filing an issue in the GitHub
web UI never runs a skill, so a GitHub-tracker project still wants them. `/crew:init` offers to
generate the four files *from* the plugin's templates, off by default, only when `tracker:` is
`github`, each with a first line:

```
<!-- Generated by /crew:init from crew <version>. Do not hand-edit: re-run /crew:init --refresh
     after a plugin upgrade, or take ownership by moving it to .claude/crew/items/<kind>.md. -->
```

`/crew:status` prints one line when the generated version differs from the installed plugin version,
which is the only drift detection that is cheap enough to be reliable.

**Three new profile keys, all optional with a stated fallback.** `templates/profile.md` grows:

```
generated: <glob>, <glob>     # or "-": files no human reviews line by line (see Size:)
size-cap: 15                  # hand-written files one task may touch; "-" disables the cap
definition-of-done: <path>    # where the project's full DoD lives; default: this file's own section
merge-authority: <who>        # who may merge; default: the author
```

`/crew:init` fills `generated:` from the scan (output directories of generator scripts, `*.g.*`,
`Generated/`, lock files, vendored client folders), and reports it as *guessed* so the user corrects
it in one edit. That is the same scan it already does for build and test commands.

## 3. The size contract, generalised

**Where the generated-file rule lives: the profile, as `generated:` globs.** Not a convention — a
convention cannot be checked and every project's generated paths differ. Not a plugin constant — the
plugin cannot know them.

**What happens in a project that declares none.** `generated: -` means **every changed file counts**.
That is the safe default: the cap stays honest, and the only cost is that a project with a large
generated surface will feel the cap as too tight and then declare its globs — which is the cheap,
self-correcting direction. Silently excluding an unknown set is the expensive one.

**What `tracker.sh` does about it: almost nothing, deliberately.** It is a tracker adapter, not a
file counter; it never sees the diff. The one mechanical check worth adding is a refusal, because it
is a grep on the body it already writes:

```
task create   → refuse when the body has no "Size:" line, or when H > size-cap (profile), unless the
                body carries an "Exception:" line instead of "Split line:"
```

The architect fills `Size:` at plan time; the lead enforces at claim time (it cannot enforce what
`tracker.sh` already refused to create); `tracker.sh` only stops an unsized task from entering the
board. With `size-cap: -` the refusal is skipped and `Size:` is still required — a number a human
reads is worth having even where nothing enforces it.

## 4. The proof map and criterion ids, generalised

**What is tracker-independent.** Criterion ids are plain integers, one sequence per story, permanent,
never reused; a withdrawn one stays in place. The only cross-reference anyone writes is the pair
*(story identity, criterion number)*. That holds on GitHub, on Azure DevOps, on Jira, on a file in
the repo. This is the minimum and it is enough.

**What breaks off GitHub, precisely — three things, one of which is real.**

1. **The reference sigil.** `#717` is GitHub's. The template writes `<story-ref> AC <n>` and the
   skills substitute per `tracker:` — `#n` for github, `AB#n` for azure-devops, `PROJ-12` for a Jira
   backend. Cosmetic, one substitution.
2. **The Proof map as a Markdown table.** Any tracker with a Markdown or rich-text body renders it.
   Where a backend cannot (a plain-text work item), the template's own fallback line applies: *the
   Proof map lives in the story's design document under the profile's `designs:` and the story body
   links to it.* Also cosmetic.
3. **The two GitHub-shaped body conventions — and this one is real.** `Story: #n` as the literal
   first line and `## Tasks` as the last section are not story-format choices; they are how
   `tracker.sh` rolls tasks up (`status()` uses `select(.body | startswith("Story: #" + n))`,
   `next()` greps `^Story: #[0-9]+`, `task_create()` appends the checklist line to the end of the
   body). Any future backend must either reproduce both or implement the rollup with its own
   parent/child links — which is what a real work-item tracker has and GitHub lacks. The templates
   therefore carry both conventions with a comment saying *why*, so a second backend's author sees
   the contract instead of guessing. Azure DevOps is not implemented (`tracker.sh` exits 2), so
   nothing is broken today; what would be needed is one adapter function, not a template change.

**The `## Proves` line is what makes the map mechanical**, on any tracker: the task states
`<story-ref> AC <n>`, the architect copies those into the story's Task column at plan time, the
engineer writes the test name into `Proven by` in the PR round, the lead ticks. No tracker feature
is used beyond editing a body.

## 6. Versioning and rollout

**Superseded in part by item 8 below** (Kris, mid-run: every story and task must have the same
setup, style, format and quality). The one-line policy stands for *old* projects and for items nobody
touches; the "rewrite on touch" half is replaced by a one-pass conform step, because a mixed board is
exactly the thing the new requirement forbids.

**The policy, one line the plugin can state:**

> An item template is read when an item is written, never applied afterwards: an item already filed
> stays valid in the shape it was filed in, and takes the current shape only when someone edits it
> for another reason.

Why that and not a migration: the shape exists to make an item readable, and re-issuing a body that
already reads well produces no information while risking detail that took design rounds to settle.
The draft's item 4 reached the same conclusion for vonk's fifteen open items by weighing three
options; this generalises it, so a project adopting at 0.7.0 with 300 open items is not facing a
rewrite either.

**Two consequences, both cheap:**

- **The lead never refuses an item for being in an old shape** — only for a missing or over-cap
  `Size:` on a task *created after* the upgrade. An older task with no `Size:` line is sized by the
  lead at claim time in a one-line comment, and split there if it must be. This is the rule that
  keeps the policy from quietly becoming a migration.
- **This project's fifteen open items** (eleven tasks under #716, four under #676) take the header
  retrofit the first draft recommended — `## TL;DR`, `Size:`, `Split line:` on all fifteen, a
  `## Proof map` on #716 and #676, bodies otherwise untouched. That is a vonk decision executed in
  vonk, not something the plugin does to a project.

`plugin.json` goes to **0.6.0**: the templates are new capability, the four profile keys are
additive with fallbacks, and the only behaviour change to an existing project is `tracker.sh`
refusing an unsized task — worth a minor bump and one line in the README.

# 7. How conformance is enforced, not just described

A template in a file is a suggestion. Three things in this repository prove it: 18 of 209 task bodies
do not begin with the line `tracker.sh` needs to roll them up, several of #719–#729 are terse where
they should be plain, and the two items that read well (#733, #717) read well because of who wrote
them, not because of a rule. So the shape needs a gate, and the gate belongs where the plugin already
refuses things.

## 7a. What `tracker.sh` checks at create time — and it refuses

`story create` and `task create` already refuse on missing flags, so refusing on a malformed body is
in character and is the cheapest possible moment: the author is still in the turn that wrote it.

**Refused at `story create`:**

| Check | Why it is mechanical |
|---|---|
| `## TL;DR`, `## Why it matters`, `## Acceptance criteria`, `## Out of scope`, `## Proof map`, `## Open questions`, `## Tasks` all present | a grep per heading |
| `## Tasks` is the last heading and its body is empty | the adapter appends there |
| TL;DR non-empty and ≤ 320 characters | two sentences, counted |
| TL;DR contains no code span, no `/` path, no item reference | the no-jargon rule, in its checkable half |
| criteria ids are `1..n`, strictly increasing, no duplicates, no gaps (a `withdrawn` line still occupies its number) | parse the ordered list |
| the Proof map has exactly one row per criterion id | set comparison |
| no template placeholder survives — no `<!-- ` comment from the template, no `<…>` angle-bracket stub | one regex, and it catches the commonest failure of all: a section left as the instruction that described it |

**Refused at `task create`:**

| Check | Why |
|---|---|
| first body line matches `Story: <sigil><n>` | the rollup depends on it — this single check retires the 18-invisible-tasks class of bug for good |
| `Blocked by:`, `Role:`, `Size:` present; `Size:` parses to integer H, integer G, integer T | the lead cannot refuse an oversized task it cannot read |
| `Split line:` **or** `Exception:` present when H ≥ 12 or T ≥ 4 | the split is chosen before the diff runs long |
| H ≤ `size-cap:` (profile, default 15) unless `Exception:` | the cap |
| `## TL;DR`, `## In one paragraph`, `## Goal`, `## Proves`, `## Files`, `## Tests (RED first)`, `## Done when` present and non-empty | a grep per heading |
| `## Files` bullet count == H; `## Tests` numbered count == T | the two numbers stop being a claim and become a count |
| `## Proves` carries at least one `AC <n>` reference | a task proving no criterion is a task that should not have been planned |
| no placeholder survives | as above |

Bug and tech-debt bodies are checked the same way against their own section lists when they are filed
through the adapter. A refusal prints the failing checks as lines, not a paragraph, so the caller can
fix and retry in one turn.

## 7b. `tracker.sh lint` — judging what already exists

```
tracker.sh lint [<n> | --all | --kind story|task|bug|tech-debt] [--quiet]
  #719  task   missing: TL;DR; Size: unparseable ("about 25 files with the generated ones")
  #724  task   Files count 9 != Size H 6
  #716  story  Proof map absent; AC 7 has three independently failable outcomes (reader check)
  187 conforming, 22 not
exit 0 when all conform, 1 when any does not
```

**Cost.** One `gh issue list --state all --limit 500 --json number,title,labels,body` per kind — two
to four API calls for this project's 209 tasks and its stories, a few seconds, no per-issue fetch
(only `show` needs one). All checks run in `jq` and `awk` on bodies already in hand. It is cheap
enough to run unprompted, which is the property that matters: a drift detector nobody runs is not a
detector.

**`/crew:status` surfaces the count**, one line: `items: 187 conforming, 22 not (tracker.sh lint
--all)`. Drift becomes visible on every status call instead of being discovered six weeks later by a
reader who cannot follow a board. Exit code 1 also lets a project wire `lint` into its own gates if
it wants to — the plugin does not decide that.

## 7c. Who fixes a non-conforming item

Three owners, by moment, and no sweep backlog:

1. **At create time — the filer.** The refusal happens inside the run that wrote the body; the role
   fixes it before the item exists. Nothing reaches the board malformed. This is where almost all of
   it is handled, permanently.
2. **At claim time — the lead, in one edit.** `claim` **warns** and prints the item's lint lines; it
   never refuses, because refusing would strand items filed before the upgrade and turn a claim into
   a migration. The lead brings the item to shape before working it: it is the cheapest moment
   (he is reading the body anyway), the smallest unit (one item), and the person with the context.
   Where a missing section needs product judgement rather than transcription — a TL;DR, a criterion
   split — the lead briefs the role that owns it, which is one short call, not a planning round.
3. **In one pass at upgrade — `/crew:conform`,** see item 8. Not a sweep *task*: a task in the
   tracker that rewrites the tracker rots, and "filing is not finishing".

## 7d. Where the machine stops

**Mechanical:** presence, emptiness, length, counts, id well-formedness, cross-count consistency
(`Files` length == H), the first-line contract, placeholder survival, and one weak proxy for jargon
(a code span, a path or an item reference inside a TL;DR).

**Not mechanical, and the plugin should not pretend otherwise:** whether a TL;DR is *understandable*
by someone who has never opened the repository; whether "Why it matters" states a reason rather than
a restatement; whether a criterion is genuinely one outcome; whether "Today, in detail" carries
enough evidence that the architect does not re-investigate; whether the Goal is a design or a
direction.

**What the crew does about the rest — two named readers, both already paid for:**

- **At refine.** `/crew:refine` step 2 already runs a parallel critique. Add `crew:technical-writer`
  to that set with one narrow question: *is every TL;DR understandable without this repository, is any
  criterion two outcomes, is any section a restatement of another*. One agent call per story, on the
  cheapest tier, and it is the only reader whose mandate is already "does the text match reality".
  The product owner integrates it in step 3 like any other critique — no new step, no new role.
- **At plan.** The architect writes the task TL;DR and "In one paragraph"; `/crew:plan` step 3
  already sanity-checks each task with its owning role. Add to that brief: *can you start from this
  body without a conversation* — which is the definition of done for the task shape anyway, asked of
  the one person who would suffer.

The lead's own check stays what it is: it reads every TL;DR cold before registering, and if it cannot
say what the item is after that one sentence, the item goes back one round. A machine cannot do this
and no reviewer should be added for it.

## 7e. "Same quality" — the smallest testable definition

Six clauses, each with its judge. An item is *conforming* when all six hold; nothing else is claimed,
and no adjective appears:

| # | Clause | Judge |
|---|---|---|
| 1 | No section is left as the instruction that described it — no placeholder text survives. | machine |
| 2 | Every section in the kind's template is present and non-empty. | machine |
| 3 | Every acceptance criterion is **independently failable**: one Then, and nothing joined by "and" that could fail on its own. | reader (product owner at refine; qa-engineer when it derives tests). The machine flags " and " inside a Then as a candidate, and a flagged criterion that is fine is left alone. |
| 4 | Every task's `## Files` list is complete enough to count, and its length equals the `Size:` H. | machine |
| 5 | Every criterion has a Proof map row, and every task names at least one criterion under `## Proves`. | machine |
| 6 | Every TL;DR is two sentences or fewer, carries no code span, path or item reference, and a reader who has never opened the repository can say what the item is. | machine for the form, technical-writer + the lead for the substance |

Clause 3 is the load-bearing one: it is what makes a criterion mappable to one test, and it is the
only clause a machine cannot own. Clauses 1, 2, 4 and 5 are the ones that actually differ between
#733 and #721 today, and all four are machine-checkable — which is why a gate closes most of the gap
Kris named without adding a single review round.

# 8. Rollout, re-judged: one pass, and the plugin ships the command

Uniformity is now the requirement, so "rewrite on touch" is the wrong answer: it guarantees a mixed
board for as long as items go untouched, which for parked items is forever. The first draft weighed
"rewrite all" as six to ten hours because it assumed every body re-issued from its design document.
That is not what conformance needs. The six clauses need **headers and counts**, not new prose:
`Size:` is the existing `## Files` list counted, `Split line:` is a judgement the architect already
made when planning the wave, the Proof maps are derivable because the task bodies already cite their
criteria, and only the TL;DRs are genuinely new text — one or two sentences each.

**Recommendation: bring all fifteen open items to the new shape in one pass, in one focused session,
and ship the command that makes the same pass cheap for the next project.**

`/crew:conform [<n> | --all]`, a new skill, half-automatic by design:

1. `tracker.sh lint --all` → the non-conforming list with the failing checks per item.
2. For each item, the **mechanical** fixes are drafted without a role: `Size:` from the `## Files`
   count, `Split line:` or the flag that one is now required, the Proof map skeleton from the
   criteria ids, the `Story:` first line for a task that lacks it, the `## Proves` line from a body
   that already cites its criteria in prose.
3. For each item that needs **text** — a TL;DR, a criterion split — it briefs the owning role
   (product owner for a story, architect for a task) with that one item and nothing else. Short
   briefs, cheapest tier, parallel across items.
4. It shows the user a diff per item and **waits**, then edits the body through the tracker. Nothing
   is rewritten silently: a script cannot write a TL;DR and must not pretend to.
5. It reports what conformed, what needed a split, and what the user declined.

**The honest cost here, unchanged from the first draft:** the pass will fail two of the eleven on
`Size:`. #721 (H ≈ 22, behaviour change, three subjects) must be split before it starts. #719 (H ≈ 20)
is largely a rename but also widens a phase enum and rewrites its reader, so the honest shape is two
tasks: the mechanical sweep as the named exception, and the phase-and-wire change as an ordinary
task. Expect one or two more splits among the eight tasks that state no count. That is work the old
shape was hiding, not work this change creates.

**The policy line, revised, replaces the one in item 6:**

> A tracker item conforms to the shape the plugin ships at the time it is filed, and the crew refuses
> to create one that does not. Items filed before an upgrade are brought to the current shape in one
> pass with `/crew:conform` — never silently, never as a background sweep, and never by refusing a
> claim on an old item.

That keeps two promises at once: the board is uniform (Kris's requirement), and no item is ever
rewritten by a machine that cannot read it.
